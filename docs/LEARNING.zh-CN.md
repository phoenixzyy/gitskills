# 知客：结构、设计与复现

这是在原有 gitskills 仓库中新增的独立项目，借助 AI 辅助实现，不是 Fork。2016 年的初始提交保留；本次代码的编写时间是 2026 年。它适合练习从业务规则到可运行应用的完整过程，不代表已经在真实企业环境投入使用。

## 业务与结构

客户保存联系信息；跟进记录属于客户，记录沟通渠道、内容与下次联系时间；工单属于客户，记录问题、优先级、截止时间与处理状态。工单事件记录创建、编辑和状态变化。

`src/domain.ts` 先定义共享类型和状态图。`api/store.ts` 负责数据验证与 SQLite 操作。`api/server.ts` 将 HTTP 请求映射到业务方法并提供构建后的静态文件。`src/App.tsx` 管理界面状态、筛选、表单和详情，`styles.css` 负责响应式展示。当前界面集中在一个文件，后续可按客户、工单、对话框拆分；没有为了展示架构而引入微服务。

一次状态变更的路径是：选择操作 → 输入原因 → 提交工单版本和目标状态 → 服务端验证状态图与版本 → 在事务内更新工单并插入事件 → 返回结果 → 界面重新读取工作区。客户端按钮限制只是提示，真正的业务约束始终在服务端。

## 关键设计原因

1. **SQLite 与本地运行**：减少环境依赖，数据写入真实数据库；不是用浏览器数组伪装持久化。仅监听回环地址，不实现公网服务或多人权限。
2. **事务**：工单成功更新但历史写入失败时必须整体回滚。测试通过人为制造审计写入失败验证这个性质。
3. **乐观版本**：两个窗口同时打开同一工单，较旧窗口不能覆盖另一窗口的更新。服务端返回 409，需要刷新后重新编辑。
4. **明确状态图**：不能从新建直接关闭。处理中可以等待或解决，等待可以恢复处理或解决，已解决可以关闭或重开，已关闭可以重开；每次需要原因。
5. **时间语义**：API 存储 UTC，界面显示本地时间。只有未解决、未关闭且截止时间严格早于当前时间才算逾期。最新跟进记录没有下次日期，表示撤销旧的联系计划。
6. **错误反馈**：失败不会假装成功或清空输入。写入成功但刷新失败时明确提醒不要重复提交。数据库约束、参数绑定、请求体大小和来源检查各负责不同边界。

## 复现

使用 Node.js 24，在仓库根目录依次运行 README 中的安装、检查、构建、测试和启动命令。首次为空工作区；`npm run seed:demo` 仅向空库加入虚构示例。可通过独立的 `DB_PATH` 建立练习数据库。

- 新建客户，添加电话跟进并设置下次联系；再添加无下次时间的跟进，观察计划清除。
- 新建截止时间已过的工单，观察逾期筛选；进入处理中，再解决，观察逾期计数减少。
- 在两个浏览器窗口打开同一工单，分别编辑；第二次提交应提示冲突，刷新后才重试。
- 重启进程，确认记录仍在；不要把练习数据库提交到 Git。
- 阅读 `tests/store.test.ts` 的事务回滚和陈旧版本测试，再看 `tests/http.test.ts` 的实际 HTTP 请求，最后看 `tests/ui.test.mjs` 的界面交互。

本次验证有 14 个 Node 测试和 4 个 jsdom 界面测试。jsdom 不是真实浏览器；焦点循环、完整键盘操作、移动端视觉效果仍需要浏览器人工检查，不应把这些测试说成完整端到端验证。

## 面试讨论与练习

- 为什么不能只在前端检查状态？直接构造 HTTP 请求能否绕过？
- 乐观锁与数据库事务解决的分别是什么问题？审计插入失败时如何保证一致性？
- 解决后关闭、关闭后重开时，解决原因应怎样变化？
- 截止时间刚好等于当前时间算逾期吗？跨时区如何定义？
- 本地应用如果改成多人服务，还缺哪些身份、权限、备份、迁移和可观测性能力？

建议练习：先增加分页和相关测试；再设计明确的数据库迁移；最后把界面按业务区域拆分。若增加导出，应考虑敏感数据、CSV 公式注入和导出范围。不要在没有测试和运行验证的情况下声称支持生产部署或大数据量。
